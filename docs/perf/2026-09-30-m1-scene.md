## 2. Evaluator cost

Scene: 1080p30 sequence with three video tracks. V1 has two 1080p clips (0 to 30 s and 30 to 60 s) with a 2 s cross-dissolve at the 30 s cut. V2 has a 4K clip scaled 0.3, rotated 5°, moved right. V3 has a 512×512 image scaled 0.2 in the top-left corner. Every frame has 3 layers, and during the dissolve the bottom layer is a transition. The unit test `scene_bench::tests::bench_scene_has_three_layers_and_a_transition_at_the_cut` checks this, so no layer is culled away.

Method: 200 batches of 100 `evaluate` calls sweep frames 0 to 1799 (all 60 s, crossing the transition twice). Each sample is the batch time / 100, because one call is below the resolution of the Windows timer. Output spec: 1920×1080, `PreviewHigh`. Microseconds.

| scenario | case | p50 | p90 | p99 | max |
|---|---|---:|---:|---:|---:|
| scene | 3 layers + transition | 0.20 | 0.26 | 0.32 | 0.43 |

To check that the numbers are stable, the command was repeated 7 more times in the same session. p50 was 0.19 to 0.20 µs every time, p90 0.25 to 0.48 µs, p99 0.32 to 1.31 µs, and max 0.42 to 2.57 µs. The spread is all in the tail, which is scheduler noise on a sub-microsecond workload.

**Verdict: target met.** Evaluator p99 is 0.32 µs in the recorded run and 1.31 µs in the worst of 8 runs. The target is p99 ≤ 50 µs, so the headroom is about 38× even in the worst run. M1 does no optimisation work. Because p99 is a percentile of 100-call means, one slow call inside a batch is averaged in. That is enough to show the evaluator does not matter against a 33 ms frame budget, but it is not a per-call worst case.

## 3. Equivalence with the legacy model

`crates/timeline/tests/scene_equivalence.rs` steps through each project in 1/7 s steps (not aligned to frames). At every step it checks that the evaluator shows exactly what the legacy `composition::video_at` showed: no layer where legacy showed nothing, and otherwise exactly one layer with the same clip and the exact same source time (`Time`, not rounded).

| scenario | result |
|---|---|
| `single_track_with_gaps_matches_video_at`: one track, four clips with different source offsets, a gap from 5.5 to 7 s and a 0.9 s clip at the end | pass |
| `opaque_upper_track_hides_the_lower_like_before`: a 10 s clip on V1 under two opaque, untransformed V2 clips (2 to 5 s and 7 to 8 s) | pass |

**2/2 green.** No divergence was found, so the evaluator was not changed. To confirm that the test can fail, two temporary mutations were tried and then reverted. Shifting the evaluator's source time by 1 ms fails both scenarios. Disabling occlusion culling fails the multi-track scenario with 2 layers where 1 is expected.

## 4. Full test suite

`cargo test --workspace`: 39 test targets (unit, integration and doc tests), **291 passed, 0 failed, 3 ignored**. The 3 ignored tests are live network calls (`kadr-ai` `live_providers`: Jev ×2, OpenAI) and are ignored by design. `cargo build --workspace` produced no warnings.

## 5. Notes for M2

Evaluation is not a cost worth optimising for M2. The allocations per call (the `layers` vector and each layer's `effects` vector, freed at the end of the call) remain the only obvious costs. If a later stage calls `evaluate` many times per frame (for example thumbnails or scrubbing prefetch), reusing a `FrameScene` would be the first step. There is no need to do it now.
