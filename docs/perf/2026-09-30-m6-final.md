# M6 final numbers: the new pipeline against M0

Recorded 2026-09-30 / 2026-10-01 on branch `feature/render-pipeline` (M6 task 2), with the legacy paths already deleted. Every number is copied from the raw output of `kadr-bench render`, `playback`, `export` and `live` (`target/release/bench/*.json`; raw stdout kept per run). M0 is [the baseline](2026-09-30-m0-baseline.md), the others are [M2](2026-09-30-m2-render.md), [M3](2026-09-30-m3-playback.md), [M5](2026-09-30-m5-export.md) (incl. its section 8 addendum).

| | |
|---|---|
| CPU | 13th Gen Intel Core i5-13420H, 8 cores / 12 threads (same machine as M0 to M5) |

**The machine was not fully quiet, and this decides how to read everything below.** No agent or build of mine ran during a measurement, but other processes outside my control did: two `du` walks of `C:\Program Files` and `AppData\Local\Programs` (from another session), Chrome and VS Code at 10 to 40 % CPU. A `render` run and three `export` runs fell into a "slow state" (4K rows 2 to 3.5x slower, `render p50` of 44 to 53 ms for a 4K full-frame export where others show 5 to 14 ms). I confirmed this is environmental and not a code regression: an M2-era build (commit `e318981`, built in a separate worktree) and the current build gave the same 4K numbers back to back (30.05 vs 31.48 ms for `4K 1 layer scaled`), and the same binary gave 97.50 to 110.01 ms in the noisy runs and 28.54 to 28.66 ms in the quiet ones. All runs are listed in section 6; the tables use the best-behaved run of each command and say which.

Runs: `render` 5, `playback` 3, `export` 5 (of which 2 quiet enough to compare), `live` 2 to 3 per configuration. `live` is at 1080p30 sequence, 60 s, `h264_1080p30.mp4` (60 s long), driven through kadr-mcp with `get_perf`; `--layers 3` and `--quality full|half|quarter` were added for this measurement (`apps/kadr-bench/src/live.rs`, commit `d5b4f2f`): quality is seeded into the isolated data dir's `settings.json`, and 3 layers means the same clip on V1, the 4K clip as a 0.3-scale PiP rotated 5 degrees on V2 (three 20 s segments end to end) and the 512x512 alpha logo at scale 0.5 on V3.

## 4. Export (`kadr-bench export`, vs M5 and M0)

The legacy exporter is deleted, so there is no same-run legacy row any more; the reference numbers are M5 (same-run legacy 101.58 fps on the M0 scenario; quiet re-run addendum section 8 of the M5 document) and M0's 133.30 fps. fps = median of 3 exports of the scenario, in a run of the `export` command; "min-max" is over those 3. crf 21 "fast", no audio.

Runs 2 and 3 were the two that matched the machine state of M5's addendum; run 3 is shown, run 2 in brackets.

Late allocations: 0 in every export row of every run.

**Flag: 4K export, -18.6 % and -20.6 % against M5's 24.59 fps** in the two runs where the other rows agree with M5 to within 3 %. The spread inside a run overlaps M5 (the best 3-run value was 24.41 in run 2 and 24.53 in run 3, equal to M5's median), the row is decode-bound (decode wait 5.03 to 11.49 s of a 10 to 15 s export; 4K full decode is the one place where the machine has no headroom, M0 section 3: 30 fps), and sequential 4K decode in `playback` is faster than in M3 (41.42 / 43.35 against 34.09 / 37.00 fps). I could not isolate a cause: the quiet-machine condition was not reproducible here (runs 4 and 5 fell to 9.58 and 9.22 fps with `render p50` of 44.00 and 52.80 ms, every row slow, and `du` processes were running). By the stage's own rule (regression over 10 % is a flag) this stays flagged and the next person to touch the export should re-measure the 4K row on a machine with nothing else running.

Against M0 §6 (legacy 133.30 fps, same scenario): new 97.83 fps is 0.73x. M5 measured the legacy exporter in the same process at 101.58 fps and, in its quiet re-run, at 67.47 and 122.41 fps (three-run spread 65 to 141): the FFmpeg graph is as load-sensitive as the new path, so the honest summary is "within the range the legacy exporter showed", not faster. The new path adds 4K at about 20 fps, three-layer export at 69.92 fps and 0 late allocations; there is no legacy number for the last two rows to compare with.
